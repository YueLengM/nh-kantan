# Minecraft 金融交易 Mod 完整改造任务书

**项目性质：** 现有 Minecraft Mod 的功能完善与市场模拟系统改造

**开发语言：** Java，遵循现有项目的版本及技术栈

**开发方式：** 由编程 Agent 检查现有代码后直接实施增量修改

**开发目标：** 实现一套具有自然市场行为、真实订单撮合、完整交易功能和简化期权系统的游戏内金融市场

**优先级：** 可玩性 > 功能完整性 > 运行稳定性 > 经济模型真实性 > 系统复杂度

# 一、项目现状与开发原则

## 1.1 现有项目

项目已经拥有可运行的 Minecraft 交易 Mod Demo，包括交易界面、行情图表和随机行情生成机制。

本次任务需要在现有实现上进行功能完善和算法改造，主要包括：

1. 用多机器人订单簿市场替换原有的完全随机行情。

2. 实现玩家与机器人共用的订单撮合。

3. 补全玩家账户、仓位、盈亏和交易记录。

4. 补全限价单、市价单、止盈止损及撤单功能。

5. 在现有图表上展示真实持仓、订单与盈亏。

6. 新增两周到期的简化欧式期权。

7. 实现期权做市商动态报价与 Delta 对冲。

8. 加入随机化的机器人行动调度，避免固定周期产生可预测交易行为。

9. 将主要市场参数集中配置，方便后续调整玩法。

## 1.2 核心开发原则

**必须先检查现有项目代码，再决定具体实现方案。**

优先阅读并理解：

- 现有 Mod 的入口、初始化及服务端生命周期。

- 图表、盘口、交易面板等 UI 组件。

- 玩家交易输入、网络同步与账户数据结构。

- 当前存档与世界数据持久化机制。

- 已有配置文件和配置加载方式。

- 当前交易品种及其价格精度、交易单位。

优先复用现有类、数据结构、UI 组件及网络机制。

已存在的功能应当直接补全或修复，避免重新开发平行系统。

**本文档中的所有 Java 代码、伪代码、数学公式、类名、配置示例均仅供参考。必须根据 Mod 现有实现进行适配，不要求机械照搬。**

允许调整内部结构，但避免无必要的大规模重构。

目标是尽量用简单代码实现完整、自然的游戏体验。

# 二、系统总体架构

## 2.1 单市场线程模型

使用一个独立市场工作线程，统一维护全部市场状态。

Minecraft 服务端主线程负责：

- 接收玩家操作。

- 验证交易请求来源和基础参数。

- 将玩家交易指令发送至市场线程。

- 将市场快照同步到客户端。

- 执行需要访问 Minecraft 世界对象的操作。

市场线程负责：

- 玩家订单处理。

- 中央订单簿维护和撮合。

- 市场机器人调度。

- 随机公允价格更新。

- 账户余额、仓位及盈亏计算。

- 止盈止损触发。

- 期权报价和 Delta 对冲。

- 期权到期结算。

- 行情快照生成。

订单簿、虚拟账户、机器人及期权仓位只能由市场线程修改。

通过线程安全指令队列传递请求，通过不可变快照向其他线程提供状态。

## 2.2 参考实现

```java
ScheduledExecutorService executor =
    Executors.newSingleThreadScheduledExecutor();
executor.scheduleAtFixedRate(
    market::tick,
    0,
    100,
    TimeUnit.MILLISECONDS
);
```

实际开发时应优先利用现有 Mod 调度基础设施，不能重复创建多个市场循环。

推荐每 100ms 执行一次基础市场更新，但该周期必须可配置。

### 玩家订单的处理

玩家订单进入市场指令队列，在下一次市场线程处理时立即撮合。

机器人不应阻塞玩家订单，市场指令队列应优先于普通机器人活动得到处理。

## 2.3 市场时间与游戏时间分离

系统使用两种时间：

**市场调度时间：**

- 用于机器人行动间隔。

- 用于做市商刷新报价。

- 用于 Delta 对冲频率。

- 默认使用单调递增的实际运行时间。

**Minecraft 游戏时间：**

- 用于期权到期。

- 用于游戏内交易日期。

- 用于与游戏世界相关的事件。

两者不能混用。

服务器暂停、世界卸载或服务端停止时，需要停止相应市场任务，避免后台线程持续修改已卸载世界的数据。

# 三、机器人随机化调度系统

这是本次改造的重点之一。

## 3.1 设计目标

**机器人必须错峰执行交易操作，不能全部在固定市场 Tick 同时下单。**

同时，机器人行动间隔必须包含随机性，不能每隔固定 500ms 或 1000ms 必然执行。

否则玩家可以通过观察固定周期，预测机器人补单、撤单及大额交易的时机，形成不合理的机械套利机会。

需要实现：

- 不同机器人拥有不同的行动周期。

- 同类机器人实例的执行时间相互错开。

- 行动间隔存在适度随机性。

- 市场环境可以影响行动频率。

- 做市商刷新和 Delta 对冲同样随机化。

- 玩家不能通过观察固定时间表稳定预测机器人下一次交易。

## 3.2 独立调度机制

每个机器人实例维护：

- `nextActionTime`：下一次行动时间。

- `baseInterval`：基础行动间隔。

- `intervalRandomness`：间隔随机程度。

- `actionProbability`：本次行动概率。

- `lastActionTime`：上一次行动时间。

初始化时为每个机器人分配随机初始偏移。

例如：

```java
nextActionTime =
    now + random.nextLong(baseInterval);
```

之后每次执行完成，重新生成下一次行动时间。

**禁止让所有机器人直接在同一个 `marketTick()` 中无条件执行交易策略。**

市场 Tick 只负责检查哪些机器人已经到达行动时间，然后触发相应策略。

## 3.3 随机行动间隔

初版可以使用简单的区间随机：

\[

\Delta t=

\Delta t_{\text{base}}\times U(1-r,1+r)

\]

其中：

- \(\Delta t_{\text{base}}\)：基础间隔。

- \(r\)：随机偏移比例。

- \(U\)：均匀分布随机数。

例如基础间隔为 500ms，随机比例为 0.4，则实际间隔在 300–700ms 之间变化。

为了进一步降低可预测性，建议支持可选的截断对数正态分布：

\[

\Delta t=\operatorname{clip}

\left(

\Delta t_{\text{base}}e^{\sigma Z-\sigma^2/2},

t_{\min},t_{\max}

\right)

\]

其中 \(Z\) 为标准正态随机变量。

默认可以采用均匀抖动，代码更简单；如果玩家仍容易预测行动时间，则切换到截断对数正态间隔。

所有参数可配置。

## 3.4 随机跳过行动

机器人到达行动时间不代表一定提交订单。

例如：

```java
if (random.nextDouble() < actionProbability) {
    trader.performAction(market);
}
```

即使决定行动，也允许策略最终选择不交易。

这样能够进一步消除机械规律。

## 3.5 市场活跃度对调度的影响

可根据市场波动和近期成交量调整机器人行动频率。

例如：

- 高波动环境中，趋势交易者更活跃。

- 低波动环境中，均值回归交易者更活跃。

- 成交量增大时，噪声交易者行动略微加快。

- 剧烈波动时，做市商可以减少报价数量或增加刷新频率。

这些调整只需要简单的系数，不需要复杂预测模型。

## 3.6 事件队列

推荐使用按下一次行动时间排序的优先队列：

```java
PriorityQueue<ScheduledMarketAction> events;
```

每次更新：

1. 优先处理玩家待执行指令。

2. 检查最早到期的机器人行动。

3. 执行对应策略。

4. 为该机器人生成下一次行动时间。

5. 重新放入队列。

6. 重复处理已到期事件，直到本轮事件预算耗尽。

7. 发布更新后的市场状态。

需要设置每次 Tick 的最大事件数量，避免大量机器人同时触发时产生卡顿。

同一轮内发生的不同事件保持各自的逻辑执行时间和先后顺序，不要将其合并成一次批量交易。

如果两个事件的计划时间完全相同，可以采用随机但可复现的顺序处理。

## 3.7 消除集中成交现象

需要特别避免以下问题：

- 所有做市商同一时间撤单。

- 所有做市商同一时间重新挂单。

- 所有噪声交易者同时提交订单。

- 多个机器人始终采用相同交易数量。

- 期权对冲始终在固定整秒发生。

- 机器人价格始终精确围绕同一中心报价。

- 所有品种在同一时刻同步出现大量交易。

应当通过随机初始偏移、随机行动间隔、随机订单数量和独立随机数状态解决。

不同机器人使用独立随机数流，允许配置全局随机种子用于调试复现。

# 四、模拟市场行情生成

## 4.1 核心机制

市场价格由真实订单成交产生。

采用以下流程：

**隐藏公允价格 → 机器人策略 → 订单生成 → 订单簿撮合 → 成交价格 → 图表。**

原有随机行情生成器不能继续直接修改最新成交价格。

## 4.2 随机公允价格

每个交易品种维护隐藏公允价格：

\[

F_{t+1}=F_t+\mu_t+\sigma\epsilon_t

\]

其中：

- \(F_t\)：隐藏公允价格。

- \(\mu_t\)：缓慢变化的漂移。

- \(\sigma\)：随机波动强度。

- \(\epsilon_t\)：标准正态随机数。

漂移采用缓慢变化的随机过程：

\[

\mu_{t+1}=

\operatorname{clip}

(\alpha\mu_t+\eta_t,-\mu_{\max},\mu_{\max})

\]

主要参数：

- 基础波动率。

- 漂移变化强度。

- 漂移持续系数。

- 最大漂移。

- 公允价格更新周期。

- 价格上下限。

建议所有价格相关参数基于 Tick Size 或价格比例表达，方便适配不同品种。

## 4.3 玩家交易对后续价格的影响

玩家大额吃单会直接改变最后成交价。

但如果隐藏公允价格完全不受成交影响，做市商可能立即回到原先价格，导致大额订单的冲击过快消失。

因此增加简单的订单流反馈：

\[

F_{t+1}=F_t+\mu_t+\sigma\epsilon_t+

\lambda I_t

\]

其中 \(I_t\) 是近期买卖主动成交量的不平衡指标，可采用指数平滑。

主动买入较多时，公允价格受到小幅向上影响；主动卖出较多时则受到向下影响。

该反馈需要限制最大幅度并随时间衰减。

这样玩家的大额交易既会即时吃穿盘口，也会对后续行情产生短暂影响。

**不能直接按照玩家买卖方向无限推高或压低隐藏价格。**

## 4.4 市场数据生成

所有市场可见数据均基于真实模拟交易：

- 最新成交价格：最后一笔撮合成交价。

- 成交量：实际成交数量。

- K 线：对应时间段内的实际成交。

- 盘口：当前有效限价订单。

- 买卖价差：最优卖价减去最优买价。

- 成交记录：撮合产生的成交事件。

没有成交的时间段，K 线可以延续上次收盘价格，成交量为零。

不允许随机生成与订单簿不一致的成交记录。

# 五、五种交易机器人

所有机器人共享相同的订单接口。

每类机器人允许配置实例数量、资金或仓位限制、基础行动周期及随机性。

## 5.1 做市商 MarketMaker

持续向市场提供买卖流动性。

策略规则：

- 围绕隐藏公允价格提供双边报价。

- 默认挂出 5–10 档深度。

- 价差随市场波动变化。

- 各档订单数量存在随机差异。

- 根据已有库存调整报价中心。

- 对过度偏离当前公允价格的订单执行撤单。

- 重新挂单时加入轻微价格和数量扰动。

- 避免每次更新时全部撤单再同时重挂。

建议采用逐步维护订单的方式：

- 部分订单保持不变。

- 部分订单随机撤销。

- 部分订单补充。

- 必要时重新定位报价中心。

这样可以形成更加稳定自然的盘口。

做市商拥有库存和挂单量上限。

为保证可玩性，可以为系统提供一个基础流动性保障机制，但不能在玩家单次吃单过程中无限补充订单。

## 5.2 趋势交易者 TrendTrader

依据近期成交价格动量交易。

\[

M=P_t-P_{t-n}

\]

上涨动量较强时倾向于买入，下跌时倾向于卖出。

动量越强，行动概率及订单数量可适当增加。

不同实例使用略微不同的观察窗口，避免产生完全同步的交易信号。

## 5.3 均值回归交易者 MeanReversionTrader

维护近期成交均价：

\[

D=P_t-SMA_n

\]

价格高于均线时倾向卖出，低于均线时倾向买入。

偏离较大时提高交易意愿。

不同实例使用不同均线长度和触发阈值。

## 5.4 噪声交易者 NoiseTrader

随机执行小额交易。

随机因素包括：

- 买卖方向。

- 是否交易。

- 订单类型。

- 订单数量。

- 限价距离。

- 下次行动时间。

主要用于形成连续交易和基础成交量。

## 5.5 巨鲸交易者 WhaleTrader

低频执行大额主动交易。

主要参数：

- 触发频率。

- 交易方向概率。

- 最小与最大交易数量。

- 市场波动影响系数。

- 最大资金或仓位规模。

单笔订单可能吃穿多档盘口，产生明显滑点和价格冲击。

巨鲸行动不能按照完全固定的周期触发。

# 六、中央订单簿与撮合引擎

## 6.1 订单簿结构

每个品种维护：

```java
NavigableMap<Long, Deque<Order>> bids;
NavigableMap<Long, Deque<Order>> asks;
```

以上仅为参考结构。

价格使用整数 Tick，数量使用整数单位。

买盘按价格从高到低排列，卖盘按价格从低到高排列。

同价订单按时间优先。

## 6.2 基本撮合规则

支持：

- 限价买单。

- 限价卖单。

- 市价买单。

- 市价卖单。

- 撤单。

- 部分成交。

限价单若能够立即成交，则先匹配对手盘；未成交部分留在订单簿。

市价单从最优对手价开始逐档成交；流动性不足时，未成交部分取消。

每笔成交必须更新：

- 买方订单。

- 卖方订单。

- 双方持仓和账户。

- 最新成交价。

- 市场成交量。

- 成交记录。

- 相关图表数据。

禁止机器人和玩家使用不同的撮合规则。

同一账户原则上不允许自成交。

## 6.3 大额订单冲击

例如卖盘：

| 价格 | 数量 |
|---|---:|
| 5000.25 | 10 |
| 5000.50 | 20 |
| 5000.75 | 30 |
| 5001.00 | 50 |

玩家市价买入 80 手时，将依次成交：

- 5000.25：10 手。

- 5000.50：20 手。

- 5000.75：30 手。

- 5001.00：20 手。

最后成交价变为 5001.00。

价格变化直接来自真实模拟撮合，不额外制造虚假的成交。

## 6.4 订单生命周期

订单状态至少包含：

- NEW：已接受。

- PARTIALLY_FILLED：部分成交。

- FILLED：全部成交。

- CANCELLED：已撤销。

- REJECTED：已拒绝。

- EXPIRED：已失效。

活动订单、成交订单和历史订单必须能在 UI 中正确显示。

# 七、玩家交易功能补全

现有 UI 如有空按钮、模拟功能或未连接服务端状态的交互，均需要补全。

## 7.1 市价单

玩家选择交易方向和数量后立即提交市价单。

实际成交价格按照订单簿流动性计算。

需要显示：

- 实际成交数量。

- 成交均价。

- 滑点。

- 未成交数量。

- 订单执行结果。

不能保证大额市价单全部在最新价格成交。

## 7.2 限价单

玩家可以设置：

- 买卖方向。

- 限价。

- 数量。

限价单进入订单簿后持续有效，直到成交或撤销。

支持部分成交和剩余挂单。

已经挂出的订单占用相应资金或保证金，撤销后释放。

## 7.3 止损与止盈

补全止损和止盈功能。

支持玩家对现有仓位设置：

- 止损价格 Stop Loss。

- 止盈价格 Take Profit。

- 对应平仓数量。

推荐实现简化 OCO 关系：

- 止盈和止损关联同一个仓位。

- 一侧完全平仓后取消另一侧。

- 一侧部分成交后，相应减少另一侧可执行数量。

- 任意情况下不能因两个保护订单连续触发而意外反向开仓。

### 止损规则

止损触发后，向撮合引擎提交对应方向的市价平仓单。

采用真实盘口成交，因此允许出现滑点。

### 止盈规则

止盈采用平仓限价单。

到达价格且存在匹配流动性时成交。

### 保护订单约束

- 止盈止损只能减少对应仓位。

- 不允许超量平仓。

- 仓位被手动关闭后自动取消相关保护订单。

- 仓位方向反转时清理旧保护订单。

- 必须正确处理部分成交。

可以通过 `reduceOnly` 标志简化保护订单逻辑。

## 7.4 平仓与反手

支持：

- 全部平仓。

- 部分平仓。

- 反向开仓。

- 一键市价平仓。

优先采用净仓位模式。

当反向交易数量大于当前持仓数量时，先平仓，再对剩余部分建立新方向仓位。

# 十、期权交易系统

## 10.1 产品规则

新增欧式看涨期权和看跌期权。

| 项目 | 规则 |
|---|---|
| 类型 | Call / Put |
| 到期时间 | 14 个 Minecraft 游戏日 |
| 卖方 | 系统期权做市商 |
| 玩家操作 | 只允许买入 |
| 提前卖出 | 不允许 |
| 提前行权 | 不允许 |
| 到期处理 | 自动现金结算 |
| 期权报价 | 理论价值 + 做市加价 |
| 期权对冲 | 系统通过标的订单簿交易 |
| 玩家最大损失 | 已支付的权利金 |

期权与现有标的资产关联。

不需要为期权单独建立订单簿。

## 10.2 合约生成

每个标的定期创建新的期权合约系列。

每个系列具有：

- 固定到期时间。

- 固定执行价。

- 固定合约乘数。

- Call 和 Put 两种类型。

执行价围绕创建时的市场价格生成：

\[

K=K_0+n\Delta K

\]

建议每个系列提供 5–9 个执行价。

执行价间距、数量、创建间隔及到期时间必须可配置。

默认每 2 个游戏日生成一批新的、期限为 14 个游戏日的期权。

同一合约系列由全部玩家共享。

## 10.3 到期时间

默认期限：

\[

14\times24000=336000

\]

即 336000 个累计游戏 Tick。

使用单调递增的游戏时间判断到期，不能使用每日循环的时间值。

对于睡觉跳过夜晚的情况，选择一种一致的时间语义，并与现有 Mod 游戏时钟保持兼容。

建议默认按实际累计游戏 Tick 计时，避免通过反复睡觉提前触发到期结算。

## 10.4 Black-Scholes 定价

采用无风险利率为 0 的简化 Black-Scholes 模型。

\[

d_1=

\frac{\ln(S/K)+\sigma^2T/2}

{\sigma\sqrt T}

\]

\[

d_2=d_1-\sigma\sqrt T

\]

看涨期权：

\[

C=SN(d_1)-KN(d_2)

\]

看跌期权：

\[

P=KN(-d_2)-SN(-d_1)

\]

其中：

- \(S\)：标的参考价格。

- \(K\)：执行价。

- \(T\)：剩余期限，以游戏年计量。

- \(\sigma\)：按游戏年计量的隐含波动率。

- \(N(x)\)：标准正态累积分布函数。

定义一个游戏年为 365 个游戏日：

\[

T=\frac{\text{剩余游戏日}}{365}

\]

波动率参数必须使用一致的时间尺度。

到期时直接使用内在价值，避免零期限数值问题。

## 10.5 简化波动率模型

不实现完整 IV 曲面，采用基础波动率及简单偏斜：

\[

\sigma(K)=

\operatorname{clip}

\left(

\sigma_0+

a|\ln(K/S)|+

b\ln(S/K),

\sigma_{\min},

\sigma_{\max}

\right)

\]

基础波动率可以由近期收益率估计，并进行指数平滑。

需要支持配置：

- 默认 IV。

- IV 最小值。

- IV 最大值。

- IV 平滑程度。

- 偏斜系数。

- 价外波动率增量。

- 波动率估计窗口。

为游戏体验，优先保证报价连续平滑，不追求完整金融市场波动率曲面。

## 10.6 做市报价

玩家只可以从系统做市商买入期权。

报价公式：

\[

Ask=

\max(

V_{\text{theory}}(1+m),

V_{\text{theory}}+p_{\min}

)

\]

其中：

- \(V_{\text{theory}}\)：理论期权价格。

- \(m\)：做市加价比例。

- \(p_{\min}\)：最小加价。

建议默认加价 3%–5%，可配置。

报价须遵守最小报价单位，并且不得低于内在价值对应的合理下限。

玩家购买时：

1. 在市场线程读取当前报价。

2. 验证报价有效性及玩家资金。

3. 扣除权利金。

4. 创建或增加期权仓位。

5. 更新系统做市商风险敞口。

6. 将对冲需求交给独立的对冲调度器。

客户端显示报价仅供预览，最终购买价格以服务端交易时的有效报价为准。

报价发生明显变化时，应向玩家正确反馈，避免 UI 显示价格与实际扣款不一致。

## 10.7 期权持仓界面

期权 UI 至少显示：

- 合约名称。

- Call / Put。

- 执行价。

- 剩余期限。

- 当前理论价格。

- 当前购买报价。

- 玩家持仓数量。

- 持仓成本。

- 当前估算盈亏。

- 到期损益。

可在 UI 中展示到期损益曲线，但优先复用已有绘图能力，不需要引入复杂图表框架。

## 10.8 到期现金结算

Call 到期收益：

\[

Payoff_C=qM\max(S_T-K,0)

\]

Put 到期收益：

\[

Payoff_P=qM\max(K-S_T,0)

\]

其中：

- \(q\)：期权数量。

- \(M\)：合约乘数。

- \(S_T\)：到期结算价。

建议使用到期前短时间窗口的有效成交价格均值，降低单笔小额交易操纵结算价的可能。

若窗口内无成交，回退到最近有效价格。

结算完成后：

- 将现金收益发放给玩家。

- 标记期权到期。

- 记录已实现盈亏。

- 更新做市商 Delta 敞口。

- 逐步调整剩余对冲仓位。

# 十一、期权 Delta 对冲系统

## 11.1 对冲原理

系统作为玩家期权的卖方，需要通过标的交易对冲方向性风险。

Call Delta：

\[

\Delta_C=N(d_1)

\]

Put Delta：

\[

\Delta_P=N(d_1)-1

\]

玩家购买 Call 后，做市商倾向于买入标的。

玩家购买 Put 后，做市商倾向于卖出标的。

## 11.2 目标对冲仓位

对全部未到期期权计算总 Delta：

\[

D=\sum_i q_iM_i\Delta_i

\]

做市商目标标的仓位为：

\[

H_{\text{target}}=D

\]

如果当前对冲仓位为 \(H\)，则需要调整：

\[

Q=H_{\text{target}}-H

\]

正数买入，负数卖出。

所有对冲交易必须通过标的订单簿执行，正常消耗市场流动性。

## 11.3 独立随机对冲调度

**Delta 对冲不能每隔固定时间机械执行，也不能每次玩家购买期权后立即无条件提交完整对冲订单。**

采用独立调度：

- 每个标的拥有自己的下一次对冲时间。

- 对冲间隔在基础周期附近随机波动。

- 对冲需求较小时可以跳过。

- 对冲规模受到单次上限限制。

- 可以分批执行对冲。

- 每批执行时间再次随机化。

- 允许根据波动率和风险敞口调整对冲频率。

例如：

- 基础间隔：1000ms。

- 随机间隔：500–1800ms。

- 最小触发 Delta 差异：可配置。

- 单批最大对冲数量：可配置。

- 对冲比例：可配置。

实际对冲量：

\[

Q_{\text{exec}}=

\operatorname{clip}

\left(

k(H_{\text{target}}-H),

-Q_{\max},

Q_{\max}

\right)

\]

其中 \(k\) 为对冲比例。

订单数量按照标的交易单位取整。

## 11.4 对冲与价格反馈

对冲使用真实模拟订单簿。

大量玩家购买 Call 时：

1. 期权做市商出现正向目标对冲需求。

2. 对冲机器人分批买入标的。

3. 买单消耗卖盘流动性。

4. 标的价格可能上涨。

5. Call Delta 随价格变化。

6. 系统在后续周期重新计算对冲需求。

购买 Put 则产生相反方向的作用。

该机制可以自然产生简化 Gamma 反馈。

## 11.5 防止反馈失控

需要限制：

- 玩家单次购买期权数量。

- 单账户期权持仓规模。

- 做市商最大 Delta 对冲仓位。

- 单批最大对冲数量。

- 对冲操作频率。

- 玩家期权交易产生的最大风险敞口。

对冲计算使用平滑参考价格，避免由于单笔成交价格的短暂波动导致连续反向交易。

同时记录做市商实际对冲成交仓位，禁止重复把完整目标仓位当作增量下单。

# 十三、交易界面的游戏体验优化

## 13.1 核心体验目标

玩家打开交易界面时应当看到持续、自然变化的市场。

不能出现：

- 所有机器人同一瞬间集中成交。

- 固定间隔突然刷新大量订单。

- 价格长时间不动，然后周期性大幅跳跃。

- 大额成交完全不影响市场。

- 成交价格与盘口显示不一致。

- UI 盈亏变化与服务端账户不一致。

- 限价单无故成交。

- 止盈止损在错误价格触发。

- 玩家平仓后图表仍保留旧仓位线。

- 期权价格更新后出现无意义的剧烈跳动。

## 13.2 行情与 UI 同步

UI 刷新频率可以低于市场内部更新频率。

例如：

- 市场内部每 100ms 更新。

- 客户端每 200ms 接收行情快照。

- 玩家下单和成交反馈优先同步。

- 图表只更新发生变化的数据。

避免每个机器人订单都触发完整 UI 重建。

## 13.3 订单提交反馈

玩家提交订单后应当获得明确结果：

- 提交成功。

- 挂单成功。

- 部分成交。

- 完全成交。

- 资金不足。

- 数量无效。

- 价格无效。

- 超过仓位限制。

- 订单已取消。

订单提交后不要只在客户端临时修改 UI。最终状态必须由服务端确认。

## 13.4 操作便利性

优先补全以下交互：

- 买入 / 卖出。

- 市价 / 限价切换。

- 数量快速调整。

- 一键平仓。

- 一键撤销活动订单。

- 设置止盈止损。

- 查看仓位盈亏。

- 查看历史成交。

- 查看期权持仓及到期信息。

尽量保持现有 UI 风格，不进行无必要的整体重新设计。

至少包括：

- 玩家账户余额。

- 玩家当前仓位及成本。

- 活动订单。

- 保护性止盈止损订单。

- 期权持仓。

## 14.2 多人交易

所有玩家共享同一标的市场订单簿。

玩家之间可以相互撮合成交。

机器人与玩家使用相同的撮合规则。

## 14.3 服务端生命周期

- 存档时取得一致的市场状态。

- 重新进入游戏后不会重复结算订单或期权。

- 玩家退出不会导致账户和活动订单异常丢失。
